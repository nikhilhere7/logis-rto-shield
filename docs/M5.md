# M5 — Order Risk Checker

M5 turns the M4 model into a tool a merchant uses at checkout. `POST /api/risk/score/` takes one order
that has not shipped yet and returns its RTO probability, a risk category, the reasons behind it, a
recommended action and how much history stands behind the score. A batch endpoint scores up to 500
orders at once. Merchants without a trained model still get a score from a transparent rule set.

Building it also exposed two faults in the M4 features, so M5 starts by fixing them (section 3).

## 1. What was built

| Piece | File | Purpose |
|---|---|---|
| Features (revised) | `ml/features.py` | Feature version 2 and the shared `derive()` |
| Training (extended) | `ml/train.py` | Risk bands, COD threshold, feature version, stale-model check |
| Scoring engine | `ml/score.py` | Live features, model or rule score, factors, category, action |
| API | `ml/views.py`, `ml/urls.py` | `OrderInput` validation, single and batch endpoints |
| Tests | `ml/test_ml.py`, `ml/test_score.py` | 19 + 7 tests |

No new tables and no migrations.

## 2. Architecture

```
order(s) ──> OrderInput (validate, normalise)
                 │
                 ▼
        score.build_features(merchant, orders)
          ├─ customer: merchant's own customer ID, else hashed phone
          ├─ prior orders placed strictly before order_ts
          ├─ resolved parcels + these orders ──> features.time_aware_history()
          ├─ pincode zone, city, tier, COD serviceability
          └─ features.derive()            ← the same function training uses
                 │
                 ▼
        scorer_for(merchant)
          ├─ current trained model ──> Scorer.predict_proba + Scorer.contributions
          └─ no model, or a stale one ──> rule_score()
                 │
                 ▼
        category (fixed bands) ─> repeat-returner policy ─> action ─> response
```

**Training and live scoring share one code path.** `derive()` turns raw facts and history counts into
model features for both, and live history comes from `time_aware_history()`, the same strictly-before
`merge_asof` training uses. On 300 real parcels, the live path rebuilt exactly the features training had
computed, with no mismatch in any column.

**Live history only uses the past.** For each order, customer and pincode outcomes count only if they
were known strictly before that order's `order_ts`, and prior orders count only those placed strictly
before it. The order being scored never counts itself, even if it was already uploaded.

Scoring only reads data. It never writes orders, customers, shipments, ledger rows, models or files.

## 3. Feature changes: version 2

Scoring single orders showed one plainly wrong result in M4: a COD customer who had returned 6 of 18
parcels scored very low and "ship as usual". Two causes:

- **Raw counts in a linear model.** `prior_orders` had no ceiling, so 18 earlier orders pushed the score
  far down. It is now `repeat_orders`, capped at 5.
- **Overlapping features.** Past deliveries, past returns and prior orders described the same thing, as
  did address words and address parts; some came out with the wrong sign. They are replaced by one
  smoothed customer return rate and a single address measure.

`cod_first_order` was added because COD risk sits mostly with first-time buyers, a combination a linear
model cannot find by itself. "Late night" is now 23:00–03:59 IST (M4 used 22:00–05:59).

**14 numeric features:** `is_cod`, `cod_first_order`, `order_value`, `order_hour`, `is_late_night`,
`is_weekend`, `repeat_orders`, `cust_rto_rate`, `pin_prior_rto_rate`, `city_tier`, `addr_commas`,
`addr_has_number`, `addr_has_landmark`, `addr_is_lowercase`.

**2 categorical:** `zone`, `sales_channel`, one-hot encoded as `zone=A`, `sales_channel=Website`, and so on.

**22 model columns** for the current merchant: the 14 numbers, then `zone=A` to `zone=E`, then
`sales_channel=Instagram Shop`, `sales_channel=Website` and `sales_channel=WhatsApp`.

`cust_rto_rate = (past returns + 3 × merchant rate so far) / (past outcomes + 3)`, so a customer with
little history sits near the merchant's average. The pincode rate keeps M4's smoothing of 20.

## 4. Feature version and stale models

Every model trained from M5 on stores `feature_version: 2` and its exact ordered `feature_columns`.
`model_feature_compatible(run)` accepts a model only if it is trained, version 2, and its columns are
the current numeric features in order followed by one-hot columns of the current categorical features.

A model trained before M5 (no version, the old 26 columns) is **stale**. It is never loaded for scoring:

- the Risk Checker scores with rules instead (`scored_by: "rules"`);
- `GET /api/ml/economics/` returns **409** with
  `{"error": "This model was trained with an older feature set.", "action": "POST /api/ml/train/ to retrain the model."}`.

Old artifacts still load with `load_artifact()`, so nothing breaks; they are simply reported as stale.

## 5. Scoring

**With a current model.** The order's features are lined up with the model's training columns, scored
with `Scorer.predict_proba` (calibrated) and explained with `Scorer.contributions`: standardised value ×
coefficient for logistic regression, LightGBM's own per-row breakdown otherwise.

**Without one** (fewer than 2,000 shipments, never trained, or stale), a rule score:

| Rule | Points (log-odds) |
|---|---:|
| Cash on delivery | +1.9 |
| First-time customer paying COD | +0.7 |
| Customer has returned parcels before | +0.8 |
| Customer has accepted 2+ parcels before | −0.9 |
| Address has no house or flat number | +0.5 |
| Very short address (under 20 characters) | +0.7 |
| COD order placed late at night | +0.5 |
| High-value COD order (over ₹2,500) | +0.4 |
| Pincode has a poor record (30+ parcels, over 30% RTO) | +0.6 |

Probability = 1 / (1 + e^−(−3.0 + points)). The weights are starting assumptions drawn from common RTO
patterns, a stopgap until a merchant has enough history to train. The response always says
`scored_by: "rules"` so nobody mistakes them for a trained model.

## 6. Risk categories

Fixed calibrated-probability cut-offs, the same for every merchant, so a category always means the same:

| Category | Probability |
|---|---|
| Low | below 10% |
| Medium | 10% to under 25% |
| High | 25% to under 50% |
| Very high | 50% and above |

They are stored as `metrics["risk_bands"]`. The six-bin calibration table from M4 is kept separately as
`metrics["bands"]`. The economic cut-off for refusing COD is reported on its own as
`metrics["cod_prepaid_threshold"]` and is never used to pick a category.

**Recommended actions**

| Category | COD order | Prepaid order |
|---|---|---|
| Low | Ship as usual. | Ship as usual. |
| Medium | Confirm the order on WhatsApp or by phone before dispatch. | Ship as usual. |
| High | Offer a prepaid discount or take a partial advance before dispatch. | Confirm the delivery address before dispatch. |
| Very high | Do not ship as COD. Ask the customer to pay online first. | Call the customer to confirm the address and that they still want the order. |

Above Low, an address with no house number and under 25 characters adds "Ask for a complete address with
house number and landmark." If the pincode is marked not COD-serviceable, a COD order is told to pay
online instead, whatever the category.

## 7. Repeat-returner policy

A COD customer who has returned **at least 2** parcels **and at least 30%** of their earlier resolved
parcels is never rated below **Medium**. If the score falls in Low, the category is raised to Medium, the
probability is left unchanged, and `policy_note` says why, for example:
"Raised from Low by policy: this customer returned 6 of 18 earlier parcels."

The probability stays honest; the band reflects a business rule layered on top of the model.

## 8. Confidence and contributing factors

**Confidence** says how much of the merchant's own history stands behind the score. It is separate from
risk: an order can be Very high risk at Medium confidence.

| Level | Needs |
|---|---|
| High | 100+ earlier parcels to this pincode and 2+ earlier orders from this customer |
| Medium | 30+ earlier parcels to this pincode |
| Low | anything else |

**Contributing factors** list up to five reasons, strongest first, each as
`{"factor", "value", "effect", "strength"}`. Factors weaker than 0.15 are left out. A zone or channel is
only mentioned for the value this order actually has. Model factors are relative to the merchant's
average order: "Customer's earlier orders: 18, lowers risk" means lower than a typical order.

## 9. API

Both endpoints use the project's `MerchantAPIView`: the user must be logged in and attached to a
merchant, and the merchant always comes from the logged-in user. A user without a merchant gets 403.

### Authentication

The API uses **Django REST Framework session and Basic authentication** (`config/settings.py`). There is
no token or JWT endpoint. In Postman, set the request's (or collection's) Authorization to **Basic Auth**
with the Django username and password of a user linked to the merchant. A `Bearer` header is not
accepted. Basic Auth sends the password with every request, so a deployed version needs HTTPS.

### `POST /api/risk/score/`

Request (only `order_value`, `payment_mode` and `pincode` are required):

```json
{"order_id": "NEW-1", "order_value": 3200, "payment_mode": "cod", "pincode": "190001",
 "address": "near temple", "phone": "9812345678", "sales_channel": "Instagram Shop",
 "order_ts": "2026-01-05T01:20:00+05:30"}
```

Response (200):

```json
{
  "order_id": "NEW-1",
  "risk_probability": 0.965,
  "risk_pct": 96.5,
  "risk_category": "Very high",
  "contributing_factors": [
    {"factor": "Cash on delivery", "value": "COD", "effect": "raises risk", "strength": 1.13},
    {"factor": "Delivery zone", "value": "E", "effect": "raises risk", "strength": 0.95},
    {"factor": "First-time customer paying COD", "value": "Yes", "effect": "raises risk", "strength": 0.83},
    {"factor": "Address parts", "value": "0", "effect": "raises risk", "strength": 0.8},
    {"factor": "Placed late at night", "value": "Yes", "effect": "raises risk", "strength": 0.4}
  ],
  "recommended_action": "Do not ship as COD. Ask the customer to pay online first. Ask for a complete address with house number and landmark.",
  "policy_note": "",
  "confidence": {"level": "Medium", "pincode_parcels_seen": 58, "customer_orders_seen": 0},
  "scored_by": "model:logistic",
  "customer": {"known": false, "previous_orders": 0, "delivered": 0, "returned": 0},
  "destination": {"pincode": "190001", "city": "Srinagar", "zone": "E",
                  "parcels_sent_before": 58, "past_rto_rate_pct": 37.9}
}
```

`parcels_sent_before` counts parcels with a known outcome (lost parcels are excluded).
`past_rto_rate_pct` is the smoothed pincode rate the model uses.

### `POST /api/risk/score-batch/`

Request: `{"orders": [ {...}, {...} ]}`, 1 to 500 orders in the same format as above.

Response (200):

```json
{"count": 3,
 "by_category": {"Low": 1, "Medium": 1, "High": 0, "Very high": 1},
 "results": [ {"order_id": "NEW-1", "risk_category": "Very high", "...": "..."}, "..." ]}
```

`by_category` always lists all four categories, and `results` keeps the input order.

### Validation

| Field | Rule |
|---|---|
| `order_value` | Required, a number ≥ 0 with up to 2 decimals |
| `payment_mode` | Required. `cod` or `cash on delivery` → `COD`; `prepaid`, `paid`, `online`, `upi`, `card` → `Prepaid`, any case. Otherwise "Use COD or Prepaid." |
| `pincode` | Required. Spaces removed, then 6 digits not starting with 0 |
| `phone` | Optional. Last 10 digits kept; must start 6–9. Used only to find the customer, never stored or returned |
| `sales_channel` | Optional. `Website`, `WhatsApp`, `Instagram Shop` matched in any case; anything else is scored as an unseen channel |
| `address`, `customer_id`, `order_id` | Optional, may be blank |
| `order_ts` | Optional ISO date-time; defaults to now |

Invalid input returns **400** with an error per field. The batch endpoint returns 400 for a body that
is not a JSON object, a missing, empty or non-list `orders`, or more than 500 orders. If any order is
invalid, the whole batch is refused and nothing is scored. Errors name the failing rows by position,
starting at 0, and list only the rows with errors:

```json
{"orders": {"1": {"payment_mode": ["Use COD or Prepaid."], "pincode": ["This field is required."]}}}
```

## 10. The trained model

Retrained through `POST /api/ml/train/` as `RiskModel` #2 for merchant 2 ("Upload Test"), with feature
version 2 and 22 columns. RiskModel #1 (M4 features) is kept but inactive and stale. Training method is
unchanged from M4: chronological 70 / 15 / 15 split, logistic regression vs LightGBM chosen on validation
AUC with a 0.005 margin for LightGBM, calibration on the validation period.

**These figures are a back-test on the newest 15% of the historical dataset, not live performance.**

| | Validation AUC | Test AUC | Test avg precision | Test Brier |
|---|---:|---:|---:|---:|
| Logistic regression (**chosen**) | **0.874** | 0.842 | 0.436 | 0.0786 |
| LightGBM (best iteration 55) | 0.870 | 0.825 | 0.409 | 0.0822 |

| Measure | M4 | M5 |
|---|---:|---:|
| Validation AUC (logistic) | 0.871 | 0.874 |
| Test AUC after calibration | 0.841 | 0.842 |
| Test Brier (average-only baseline 0.0997) | 0.0789 | 0.0787 |
| Riskiest 10% of orders hold | 41.9% of RTOs | 42.6% |
| Best COD threshold / net saving | 0.35 / ₹24,787 | 0.35 / ₹25,522 |

The aggregate metrics barely moved. The fix mattered for individual answers, not for the AUC: a good
AUC can hide a model that gives indefensible answers on single orders.

**Calibration on the test period:**

| Score band | Orders | Avg predicted | Actual RTO rate |
|---|---:|---:|---:|
| 0–5% | 1,355 | 1.6% | 2.4% |
| 5–10% | 229 | 7.5% | 7.4% |
| 10–20% | 313 | 14.3% | 18.2% |
| 20–35% | 206 | 25.9% | 24.8% |
| 35–50% | 89 | 42.5% | 46.1% |
| 50%+ | 106 | 62.2% | 55.7% |

**Most important features:** cash on delivery (33.0%), delivery zone (13.5%), first-time customer paying
COD (13.1%), customer's earlier orders (12.3%), address parts (9.5%).

**Economics (default assumptions):** 908 COD orders in the test period, 215 RTOs. At the 0.35
threshold, 195 orders are flagged and 100 RTOs caught; ₹44,212 saved against ₹18,690 of margin lost, net
**₹25,522**. `cod_prepaid_threshold` is 0.35.

## 11. Results from Postman testing

Run against merchant 2 with RiskModel #2 active, authenticated with Basic Auth.

| Scenario | Risk | Category | Confidence | Action |
|---|---:|---|---|---|
| Risky: new customer, COD, Srinagar (zone E), "near temple", 01:20 | 96.5% | Very high | Medium | Do not ship as COD; ask for a complete address |
| Safe: CU03141 (18 orders, none returned), prepaid, full address | 0.4% | Low | High | Ship as usual |
| Repeat returner: CU02880 (6 of 18 returned), COD | 7.3% | Medium (raised by policy) | High | Confirm on WhatsApp or by phone |

- The risky order's factors were COD, zone E, first-time customer paying COD, an address with no
  parts, and placed late at night.
- `POST /api/risk/score-batch/` scored all three in one call, with categories and probabilities matching
  the single calls.
- Batch validation returned 400 for an empty batch, a missing `orders`, a body that was not an object,
  an `orders` value that was not a list, and a batch containing an invalid order.

## 13. Limitations

- **The top of the range runs hot.** Orders scored above 50% came back about 56% of the time against a
  predicted 62%. The ranking is right, but a 96.5% score means "very likely", not a precise figure.
- **In-flight orders are invisible.** History only counts parcels with a final outcome. A customer who
  placed five COD orders this morning looks the same as one who placed none.
- **Address history.** Training uses each customer's latest stored address and pincode; live scoring uses
  the address on the order. They match for new customers but can differ for repeat ones.
- **Ties.** Training counts earlier orders by sorted position; live scoring counts strictly earlier
  timestamps. Two orders from one customer at the same second can differ by one.
- **Unknown sales channels** score as "no channel" rather than being refused.
- **Rule weights are assumptions**, not learned from the merchant's data.
- **Speed.** Each call reads the merchant's full parcel history, about half a second on 15,000 parcels.
  That is fine now, but worth caching as volume grows.
- **The data is synthetic or derived**, so real merchants may see weaker separation. Retrain regularly,
  and treat back-test savings as an estimate, not a promise.
- **Basic Auth** sends the password with every request; production needs HTTPS or a token scheme.
